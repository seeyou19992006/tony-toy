# 2026-11-24

## 各手柄 Home 键的原始 HID 位置（实测，两个项目共用同一张表）

| 手柄 | vendor | product | report ID | 字节 | 位 | 命中值 |
|---|---|---|---|---|---|---|
| Switch Pro Controller | `0x057e` | `0x2009` | `0x30` | `data[4]` | bit4 | `0x10` |
| Stadia Controller | `0x18d1` | `0x9400` | `0x03` | `data[2]` | bit4 | `0x10` |

两者都落在 bit4、值都是 `0x10`，但**字节索引不同**。Stadia 的 `data[4]` 是 `0x79`（摇杆中位），
拿 Switch 的偏移去读会永远判成"按着 Home"——这就是最早那次"按一次连触发几十次"的来源之一。

实现上按 vendor/product 查表（`HomeKeySpec.resolve` / `RawHomeSpec.resolve`），
**未适配的型号直接跳过不注册回调**，宁可没反应也不能用错偏移去猜。

注意两家的报告节奏不一样：
- Switch Pro 是**持续上报**（66Hz，`data[1]` 是递增计数器），启动就有基线帧。
- Stadia 是**事件驱动**，不按键几乎不发报告，所以它的"第一份报告"很可能就是按下那一刻。
  因此 MacDeck 里的 `primed` 基线逻辑要带时间窗口：只有启动后 1.5 秒内收到的首帧「按下」
  才算拉起瞬间的残留，窗口外必须正常触发，否则表现为"启动后第一次按没反应"。

### 诊断方法（下次加新手柄照这个来）

写个 IOHIDManager 小程序，逐设备、逐 reportID 记录上一帧，只在字节变化时打印 diff。
两个坑：
1. **必须按设备分开存上一帧**，共用一个 buffer 会让两台手柄互相覆盖。
2. **计数器字节会掩盖按键字节**。Pro 的 `data[1]` 每帧都 +3，如果 diff 输出在一行里，
   用 `grep -v "b1:"` 过滤会把同时变化的 `b4` 一起滤掉，看起来"按键没被检测到"。
   要直接 `grep "b4:"` 找。

## Home 键方案回退：托管不抢占（推翻前一晚的"全交给 TonyToy"）

前一版把 Home 完全移交 TonyToy（TonyToy 监听 → 投 DistributedNotification → MacDeck 翻转可见性），
实测走不通，根因不在通知链路，而在 macOS 的**窗口激活 + 后台节流**：

- `NSApp.activate(ignoringOtherApps:)` 从 macOS 14 起是协作式的，后台进程的激活请求被静默拒绝。
  窗口 `isVisible=true` 但 `occlusionState` 没有 `.visible`，CGWindowList 里根本找不到 —— 表现为
  「按了没反应，动一下鼠标才出来」。改用 `NSRunningApplication.activate(options: .activateAllWindows)` 才真上屏。
- `NSAppSleepDisabled` / `beginActivity` 都压不住长时间后台后的 RunLoop 停摆，
  DistributedNotification 无队列，挂起期间投过去就丢。

**结论**：跨进程投递这个环节天生不可靠，不要拿它当主通路。

### 现在的分工

- **MacDeck 在跑** → Home 由 MacDeck 自己监听处理，TonyToy 什么都不做。
- **MacDeck 没跑** → TonyToy 拉起它（带 `--show-deck` 直接展开大屏）。
- 两边互不干扰，也不存在双触发。

### MacDeck 侧

- `ControllerInput.swift` 恢复原始 HID 通道（`git show HEAD:./Sources/MacDeck/ControllerInput.swift` 取回），
  但修了两个原始缺陷：
  1. **每台手柄独立 buffer + 独立状态**。原来全局共用一块 buffer 和同一个 `lastHomePressed`，
     接两个手柄（Pro Controller + Stadia）时报告交替覆盖，Home 位来回翻转，一次按键连触发几十次。
     现在用 `RawDevice` 类封装，context 传 RawDevice 指针。
  2. **首个报告只对齐基线不触发**（`primed`）。按需启动时拉起那一刻用户往往还按着 Home，
     不这样处理大屏刚亮就被自己关掉。
- `defaultHotkeyChord` 恢复 `[13]`；`DeckConfig.init(from:)` 去掉 filter 13；`updateChord` 去掉过滤。
- 删除 toggle 通知监听，保留 `showDeck`（重复打开 app 用）。
- 保留：`NSAppSleepDisabled`（大屏收起后原始 HID 报告要照常进来）、`beginActivity`、
  `NSRunningApplication.activate` 的上屏修复、`--show-deck` 启动参数。
- **空闲退出已全部删除**（用户要求）。MacDeck 一旦启动就常驻不退出。

### TonyToy 侧

- `AppAction.toggleApplication` → `ensureApplicationRunning(bundleIdentifier:)`：
  在跑就直接返回（交给对面自己处理），没跑才 `NSWorkspace.openApplication` 带 `--show-deck`。
  配置里 `toggle_application` 和 `launch_application` 两个 kind 都认，旧配置不用迁移。
- 保留 1.5 秒拉起抑制窗口（拉起时按键沿会连冒几次，重复拉起无意义）。
- `HomeKeyBridge` 保持每设备独立 `DeviceContext`（这个实现是对的，用户确认监听没问题）。
- 去掉排查用的 `NSSound.beep()` + 系统通知弹窗。
- 菜单栏项改名「Switch Home 拉起 MacDeck（未运行时）」。

### 踩的坑

1. **配置文件把 hotkeyChord 改成了 `[]`**。前一晚为了适配 TonyToy 方案用脚本写进去的，
   恢复代码后 `?? defaultHotkeyChord` 不会生效（配置里有值就不走默认），
   表现为 Home 完全没反应。改配置时必须一起改回来 / 删掉这个 key。
2. **`./build.sh | grep | head` 会 SIGPIPE 掉构建脚本**，卡在签名之前，app 包里留旧二进制。
   项目 memory 里记过这条，这轮又踩了一次。现在统一 `> /tmp/xxx.log 2>&1` 再 grep。
3. **安装时旧进程还活着，测的是旧代码**。`open -a` 会复用已运行实例（LaunchServices），
   而且 TonyToy 可能在覆盖安装前就把它拉起来了（带 `--show-deck`，看进程 lstart 比文件 mtime 早）。
   判断版本要看**进程启动时间 vs 二进制 mtime**，别信日志内容。
4. `strings` / `grep -a` 抓不到 Swift 二进制里的中文字符串，不能用来判断版本。

## MacDeck 空闲自动退出（已加回，实测通过）

**判定标准只有一个：多久没再唤起大屏。**（老孙 2026-11-24 明确要求）
大屏收起后开始倒计时，期间再唤起一次就取消；收起后 N 分钟没被用过就退出。

**故意不把手柄按键算作活动** —— 手柄一直连着 Mac 时，玩别的游戏、随手按两下都会重置计时，
进程永远退不掉。真正说明"还要用大屏"的信号只有"又把大屏唤起来了"这一件事。
所以 `DeckStore` 里没有 `onActivity` 回调，`handleKey` 也不参与计时。

配置 `idleExitMinutes`，默认 10，0 = 常驻不退出。设置页给了 常驻 / 5 / 10 / 30 四个按钮。

- 触发点：大屏收起时开始计时（`onVisibilityRequest` 的 false 分支），显示时取消。
  启动就是隐藏态时也会排一次（`else` 分支），否则那个进程会一直挂着。
- 不退出：大屏可见、`mouseMode` 为真（正在当鼠标用）时不算空闲。
  **大屏一直开着就不退出**（开着就当他还在用，突然黑屏更糟）。
- 到点 `NSApp.terminate(nil)`，退出前再确认一次状态。

这次能安全加回来，是因为 Home 已经走**进程内 HID 回调**了，不再依赖跨进程通知——
之前那版退掉之后唤不醒，就是因为 DistributedNotification 在后台挂起时会被丢。

实测：配置 1 分钟，`01:03:10.843` 开始计时 → `01:04:13.839` 退出，63 秒，精确。
