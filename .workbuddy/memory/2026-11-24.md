## 各手柄 Home 键的原始 HID 位置（实测，两个项目共用同一张表）

| 手柄 | vendor | product | report ID | 字节 | 位 | 命中值 |
|---|---|---|---|---|---|---|
| Switch Pro Controller | `0x057e` | `0x2009` | `0x30` | `data[4]` | bit4 | `0x10` |
| Stadia Controller | `0x18d1` | `0x9400` | `0x03` | `data[2]` | bit4 | `0x10` |

两者都落在 bit4、值都是 `0x10`，但**字节索引不同**。Stadia 的 `data[4]` 是 `0x79`（摇杆中位），
拿 Switch 的偏移去读会永远判成"按着 Home"——这就是最早那次"按一次连触发几十次"的来源之一。

实现上按 vendor/product 查表（`HomeKeySpec.resolve` / `RawHomeSpec.resolve`），
**未适配的型号直接跳过不注册回调**，宁可没反应也不能用错偏移去猜。

注意两家的报告节奏不一样：
- Switch Pro 是**持续上报**（66Hz，`data[1]` 是递增计数器），启动就有基线帧。
- Stadia 是**事件驱动**，不按键几乎不发报告，所以它的"第一份报告"很可能就是按下那一刻。
  因此 MacDeck 里的 `primed` 基线逻辑要带时间窗口：只有启动后 1.5 秒内收到的首帧「按下」
  才算拉起瞬间的残留，窗口外必须正常触发，否则表现为"启动后第一次按没反应"。

### 诊断方法（下次加新手柄照这个来）

写个 IOHIDManager 小程序，逐设备、逐 reportID 记录上一帧，只在字节变化时打印 diff。
两个坑：
1. **必须按设备分开存上一帧**，共用一个 buffer 会让两台手柄互相覆盖。
2. **计数器字节会掩盖按键字节**。Pro 的 `data[1]` 每帧都 +3，如果 diff 输出在一行里，
   用 `grep -v "b1:"` 过滤会把同时变化的 `b4` 一起滤掉，看起来"按键没被检测到"。
   要直接 `grep "b4:"` 找。

## Home 键方案回退：托管不抢占（推翻前一晚的"全交给 TonyToy"）

前一版把 Home 完全移交 TonyToy（TonyToy 监听 → 投 DistributedNotification → MacDeck 翻转可见性），
实测走不通，根因不在通知链路，而在 macOS 的**窗口激活 + 后台节流**：

- `NSApp.activate(ignoringOtherApps:)` 从 macOS 14 起是协作式的，后台进程的激活请求被静默拒绝。
  窗口 `isVisible=true` 但 `occlusionState` 没有 `.visible`，CGWindowList 里根本找不到 —— 表现为
  「按了没反应，动一下鼠标才出来」。改用 `NSRunningApplication.activate(options: .activateAllWindows)` 才真上屏。
- `NSAppSleepDisabled` / `beginActivity` 都压不住长时间后台后的 RunLoop 停摆，
  DistributedNotification 无队列，挂起期间投过去就丢。

**结论**：跨进程投递这个环节天生不可靠，不要拿它当主通路。

### 现在的分工

- **MacDeck 在跑** → Home 由 MacDeck 自己监听处理，TonyToy 什么都不做。
- **MacDeck 没跑** → TonyToy 拉起它（带 `--show-deck` 直接展开大屏）。
- 两边互不干扰，也不存在双触发。

### MacDeck 侧

- `ControllerInput.swift` 恢复原始 HID 通道（`git show HEAD:./Sources/MacDeck/ControllerInput.swift` 取回），
  但修了两个原始缺陷：
  1. **每台手柄独立 buffer + 独立状态**。原来全局共用一块 buffer 和同一个 `lastHomePressed`，
     接两个手柄（Pro Controller + Stadia）时报告交替覆盖，Home 位来回翻转，一次按键连触发几十次。
     现在用 `RawDevice` 类封装，context 传 RawDevice 指针。
  2. **首个报告只对齐基线不触发**（`primed`）。按需启动时拉起那一刻用户往往还按着 Home，
     不这样处理大屏刚亮就被自己关掉。
- `defaultHotkeyChord` 恢复 `[13]`；`DeckConfig.init(from:)` 去掉 filter 13；`updateChord` 去掉过滤。
- 删除 toggle 通知监听，保留 `showDeck`（重复打开 app 用）。
- 保留：`NSAppSleepDisabled`（大屏收起后原始 HID 报告要照常进来）、`beginActivity`、
  `NSRunningApplication.activate` 的上屏修复、`--show-deck` 启动参数。
- **空闲退出已全部删除**（用户要求）。MacDeck 一旦启动就常驻不退出。

### TonyToy 侧

- `AppAction.toggleApplication` → `ensureApplicationRunning(bundleIdentifier:)`：
  在跑就直接返回（交给对面自己处理），没跑才 `NSWorkspace.openApplication` 带 `--show-deck`。
  配置里 `toggle_application` 和 `launch_application` 两个 kind 都认，旧配置不用迁移。
- 保留 1.5 秒拉起抑制窗口（拉起时按键沿会连冒几次，重复拉起无意义）。
- `HomeKeyBridge` 保持每设备独立 `DeviceContext`（这个实现是对的，用户确认监听没问题）。
- 去掉排查用的 `NSSound.beep()` + 系统通知弹窗。
- 菜单栏项改名「Switch Home 拉起 MacDeck（未运行时）」。

### 踩的坑

1. **配置文件把 hotkeyChord 改成了 `[]`**。前一晚为了适配 TonyToy 方案用脚本写进去的，
   恢复代码后 `?? defaultHotkeyChord` 不会生效（配置里有值就不走默认），
   表现为 Home 完全没反应。改配置时必须一起改回来 / 删掉这个 key。
2. **`./build.sh | grep | head` 会 SIGPIPE 掉构建脚本**，卡在签名之前，app 包里留旧二进制。
   项目 memory 里记过这条，这轮又踩了一次。现在统一 `> /tmp/xxx.log 2>&1` 再 grep。
3. **安装时旧进程还活着，测的是旧代码**。`open -a` 会复用已运行实例（LaunchServices），
   而且 TonyToy 可能在覆盖安装前就把它拉起来了（带 `--show-deck`，看进程 lstart 比文件 mtime 早）。
   判断版本要看**进程启动时间 vs 二进制 mtime**，别信日志内容。
4. `strings` / `grep -a` 抓不到 Swift 二进制里的中文字符串，不能用来判断版本。

## MacDeck 空闲自动退出（已加回，实测通过）

**判定标准只有一个：多久没再唤起大屏。**（老孙 2026-11-24 明确要求）
大屏收起后开始倒计时，期间再唤起一次就取消；收起后 N 分钟没被用过就退出。

**故意不把手柄按键算作活动** —— 手柄一直连着 Mac 时，玩别的游戏、随手按两下都会重置计时，
进程永远退不掉。真正说明"还要用大屏"的信号只有"又把大屏唤起来了"这一件事。
所以 `DeckStore` 里没有 `onActivity` 回调，`handleKey` 也不参与计时。

配置 `idleExitMinutes`，默认 10，0 = 常驻不退出。设置页给了 常驻 / 5 / 10 / 30 四个按钮。

- 触发点：大屏收起时开始计时（`onVisibilityRequest` 的 false 分支），显示时取消。
  启动就是隐藏态时也会排一次（`else` 分支），否则那个进程会一直挂着。
- 不退出：大屏可见、`mouseMode` 为真（正在当鼠标用）时不算空闲。
  **大屏一直开着就不退出**（开着就当他还在用，突然黑屏更糟）。
- 到点 `NSApp.terminate(nil)`，退出前再确认一次状态。

这次能安全加回来，是因为 Home 已经走**进程内 HID 回调**了，不再依赖跨进程通知——
之前那版退掉之后唤不醒，就是因为 DistributedNotification 在后台挂起时会被丢。

实测：配置 1 分钟，`01:03:10.843` 开始计时 → `01:04:13.839` 退出，63 秒，精确。

## 按键追踪：关窗口崩进程（两个独立原因）+ 手柄追踪

**现象**：点「按键追踪…」窗口的关闭按钮，TonyToy 整个进程消失。

**原因一：NSWindow 过度释放**（第一次修）
`NSWindow(contentRect:)` 的 `isReleasedWhenClosed` 默认 **true**，关闭时 AppKit 自动
release 一次；但 `KeyTracePanel` 用 `self.window` 强引用持有，于是多减一次引用计数。
崩溃栈：`objc_release → AutoreleasePoolPage::releaseUntil → -[NSApplication run]`。
修：`window.isReleasedWhenClosed = false`。

**原因二：EventTap 拆除不彻底**（真正的主因，第一次修完还崩）
`stop()` 只做了 `tapEnable(false)`，没移除 run loop source、没 `CFMachPortInvalidate`。
`InputRegistry` 存的是 `WeakTap`，所以 `observer = nil` 之后 EventTap 真的被释放，
而 source 的 refcon 是 `passUnretained` → 系统队列里那个在途事件回调直接踩野指针。
崩溃栈：`_StringGuts.append → EventTap.dispatch → processEventTapData`
（就是 `dbg("tap[\(name)]...")` 在拼 name）。
修：`EventTap` 保存 `runLoopSource`，`teardown()` 严格按「停 tap → 摘 source →
invalidate port → 清引用」执行，`deinit` 也走同一条路径。

**顺带**：
- `windowWillClose` 里不再把 window/textView 置 nil（关闭流程中释放窗口同样悬垂），
  窗口留着复用，`show()` 里补 `if !isTracing { startTracing() }`。
- 追踪文本改增量 `textStorage.append`，原来是每次 `textView.string = 全量`（O(n²)），
  连续按键会把主线程卡住 → tap 超时 → 正好触发上面那条崩溃路径。
- `GamepadTrace`：手柄全键追踪。Home 走 HomeKeyBridge 的**旁听者**（不动
  `onHomePressed`，那是 GamepadFeature 的），其余键走 GameController。
  GameController 只在追踪窗口打开时创建，关掉即销毁。
  `GPPhysicalInputProfile.buttons` 是 `[String: 按钮]`，`allButtons` 是 `Set`（无 key）。

**自测入口**（以后别麻烦人手动复现）：
`./dist/build/TonyToy.app/Contents/MacOS/TonyToy --keytrace-selftest`
跑 20 轮「打开→关闭释放→灌 100 个键」，正常结束退出码 0。
对照验证过：把 `teardown()` 里的 removeSource/invalidate 撤掉，第 2 轮就 SIGSEGV(139)；
修回来 20 轮全过。

**面板工具栏**：顶部加了「清空」「暂停」。暂停只让 `append` 早退、不写文本，
tap 照常跑（停掉重建会有延迟和状态丢失，而暂停的用途只是"别滚，让我看清"）。
工具栏自己的提示走独立的 `writeLine`，绕过暂停，否则暂停时连"已暂停"都写不进去。
窗口标题同步显示「（已暂停）」。重开面板会强制恢复成继续。

## MacDeck：ABXY 布局是**真实映射**，不只是显示

老孙原话："不是只改显示，而是改大屏模式的映射，比如我用的 xbox 手柄，但我习惯了 ns
键位，那我要强制把最右边的按键映射成 A（手柄上印刷的其实是 B）"。

**设计**：`ABXYLayout` 一张表同时干两件事 —— 画图（哪个位置显示哪个字母）和出码
（哪个位置出哪个键码）。两者必须同源，否则会出现"图上写着 A、按下去当成 B"。

- `HandleKind`（nintendo / xbox）按 `vendorName` 二分：含 "pro controller" /
  "joy-con" / "switch" 算任天堂，其余（Xbox 的 "Controller"、Stadia）算 xbox。
- `ABXYLayout.native(for: kind)` = 该手柄出厂排布，用来判断"这颗键物理在什么位置"。
- `ABXYLayout.remap(labelCode, kind:mode:)`：标签码 → 原生位置 → 目标布局的码。
  auto 时目标等于原生，绕一圈还是原值，可以无脑走这条路。
- `ControllerInput.bindFace` 在**按下时**查 `self.abxyMode`（不是绑定时的值），
  所以设置里改布局下一次按键就生效，不用把已绑的手柄拆了重绑。
- 切布局时清 `pressedKeys`（ControllerInput）和 `heldKeys`/`layoutPressed`（DeckStore）：
  按着的键松开沿会用新码，跟按下时的旧码对不上，不清会卡在按下态。

**核心用例**（Xbox 手柄 + 任天堂模式，8/8 通过）：
印着 B（物理最右）→ A 确认 / 印着 A（最下）→ B 返回 /
印着 X（最左）→ Y 设置 / 印着 Y（最上）→ X 清内存。
Switch Pro 在任天堂模式下不变；Switch + Xbox 模式则反过来。

**别踩回去**：这套是输入层的活，不是 SwiftUI 显示层。改 `ABXYLayout` 的常量
就等于同时改了图和行为，改一处两处都对。自测 `--settings-test` 末尾有
`logRemapCases()`，跑一遍就知道有没有错位。

## MacDeck：布局模式改成三选一互斥（按品牌分别强制）

老孙要的语义：**原始布局 / 强制 Xbox 用 NS 布局 / 强制 NS 用 Xbox 布局**，
三种互斥，且每种只影响目标那一类手柄。

中途我先实现成「两个正交开关（可同时开＝互换）」，被否掉——他要的就是三选一。

`ABXYLayoutMode` 的 case 从 `auto/xbox/nintendo` 换成
`native/xboxAsNintendo/nintendoAsXbox`：

- `ABXYLayout.resolve(for:kind:mode:)` 里加了"模式只覆盖对应品牌"的判断，
  未被覆盖的一类永远走 `native(for: kind)`。这就是"改 Xbox 不影响 NS"的落点。
- `remap` 不用改：它先按原生排布求物理位置，再查目标布局，绕不绕得回来都自洽。
- 旧配置的 `auto/xbox/nintendo` 在 `DeckConfig.init(from:)` 里迁移：
  auto→native，旧 xbox→nintendoAsXbox，旧 nintendo→xboxAsNintendo。

设置页键位面板改成三张卡片，**每张画的是"这个模式作用在哪类手柄"**，
而不是"当前手柄会变成什么样"——否则只接 Xbox 时第三张会显示成 Xbox 的样子，
让人以为它也在改 Xbox。三张图的 caption 分别是「当前手柄的出厂排布」
「只影响 Xbox 手柄」「只影响 Switch 手柄」。

自测 `logRemapCases()` 扩到 14 条，每个模式都同时验「目标手柄被改」和
「另一类原样不动」，14/14 通过。

  可靠做法是 `run_in_background` 直接执行

## MacDeck：切键位时无限连发（修完，有回归自测）

**现象**：焦点停在「ABXY 面键映射」这类 ←→ 调值的行，按一下方向键就自己无限切换。

**根因（两处叠加，缺一不可）**：
1. `ControllerInput.abxyMode` 的 `didSet` 会 `pressedKeys.removeAll()`，而 `emit`
   的松开沿是 `guard pressedKeys.contains(key)` —— 集合被清，**松手事件被当成
   "从没按下过"直接丢弃**，上层根本收不到。
2. `setABXYLayout` 也清了 `heldKeys`，而设置页连发计时器只有收到松手才 `stop`。

第一处是关键。当时清 `pressedKeys` 的出发点是"换布局后按着的键，松开沿会用新码，
跟旧码对不上会卡在按下态"，但**清空去重集合本身就是在制造丢帧**。

**正确解法**：面键按下时算一次码并记住（`FaceButtonState`），松开沿用同一个码。
配对天然成立，于是 `pressedKeys` 完全不需要清。`setABXYLayout` 也不再动
`heldKeys` / `layoutPressed`，改成显式 `stopSettingsRepeat()`。

**另外加的兜底**：连发计时器每拍校验"那颗键还在 `heldKeys` 里"（原先只校验
`mode == .settings`），外加 6 秒上限。以后任何路径再漏掉松手沿，最多刷 6 秒。

**回归自测**：`--repeat-test`（要配 `--show-deck`，否则 `guard isVisible` 挡住）。
按住 → 连发 1.2 秒 → 松手 → 采样三次。实测 `native → xboxAsNintendo →
nintendoAsXbox` 后停住，三次采样同值、计时器均已停。

**教训**：`emit` 里的 `guard contains` 是"成对事件"的守门人，任何地方清空这个
集合都等于把在途的松开沿判成孤儿。要去重的是**物理按键**，不是逻辑码。

## MacDeck：Xbox 排布时面键带原色

判据是**最终生效的排布**，不是手柄品牌：`ABXYLayout.isXboxStyle`（`self == .microsoft`）。
所以 Xbox 手柄 + 原始布局会彩色，任天堂手柄 + 「NS 用 Xbox 键位」也会彩色；
任天堂排布一律单色（NS 按键本来就是黑白灰，上色反而假）。

  所以只要排布是 Xbox，上色位置天然就是 Y上/X左/B右/A下。
- **样式是「黑底 + 彩色字母」**（老孙纠正过一次，我最初做成彩色底白字）。
  底色 `Color.black.opacity(0.55)`，字母用 tint，描边用 tint 的半透明版本
  给黑圆一个轮廓，否则和深色大屏糊在一起。四色要够亮（绿 .45/.83/.31、
  红 .96/.33/.28、蓝 .25/.57/.99、黄 .99/.79/.22），压在深底上才看得清。
- 按下态：底色透出 22% 键色 + 描边加亮 + 外发光（设置页再微放大），
  字母颜色始终不变。
- 只改了 `KeypadPreview`（设置页）和 `keyCircle`（大屏）两处渲染，
  上色判断都在各自的 layout 局部变量上，调用方不用传参数。

验证截图：大屏左上角是黑底圆 + Y黄/X蓝/B红/A绿。提交 `66756a6`。

## MacDeck：「配置没持久化」其实是摇杆漂移在改配置

用户报"键位布局一重启就没了"。**持久化本身没问题**——实测写入
`xboxAsNintendo` → 重启 app → 仍是 `xboxAsNintendo`，`ConfigStore.save`
也是 `save(config)` 用当前内存，没有旧快照覆盖的路径。

真凶在日志里：

```
00:05:40.668 按键 左摇杆 → 按下
00:05:40.669 面键布局 → xboxAsNintendo
00:05:40.820 按键 左摇杆 → 松开
00:05:41.058 按键 左摇杆 → 按下
00:05:41.058 面键布局 → nintendoAsXbox
```

没人碰手柄。摇杆停在死区临界值，读数在 0.45 上下抖，单阈值来回穿越，
每穿一次发一个方向键，设置页就"调一格值"并写盘。

**修法：死区加滞后（hysteresis）**。进入方向要越 0.45，退出要落到 0.32 以下，
中间这段是缓冲区。停在临界值时只会停在一个状态。

实测同一颗手柄：修复前 70 秒几十条摇杆事件，修复后 70 秒 0 条。

把用户选好的模式冲掉了，看起来更像"没持久化"。以后自测一律
`env MACDECK_CONFIG_DIR=/tmp/macdeck-test ...`。

**教训**：这类"设置自己变了"的反馈，先翻日志找 `按键 xxx 按下` 的节奏——
如果间隔均匀、没人操作也对得上，就是输入层噪声，不是持久化问题。
提交 `c6dacf4`。

## MacDeck：每次按键都核对当前手柄

原来"当前手柄"只在**原始 HID 收到 Home** 时才更新，其余按键不认设备 →
接两台手柄时显示的永远是"最近按过 Home 的那台"。

根因是 `GCControllerButtonInput` 的回调只给 `(input, element, pressed)`，
**不带设备**。解法：`bind(_ controller:)` 时把 `controller.vendorName`
捕获进每个按键闭包，一路传到 `emit(_:pressed:from:)`，按下时调
`setActiveController(device, reason: "按键")`。

两个注意点：
- **`setActiveController` 只在真的换了才 `notifyDevices()`**。每次都通知
  等于每次按键都让大屏整屏重绘，连按掉帧。用户说"每次都要重新渲染"，
  但实际需求是"显示的必须是当前在操作的那台"，变了才画效果相同且不卡。
- **左摇杆不参与判定**。漂移会持续上报，让它在两台手柄间来回抢身份，界面会抖。
  只有按钮（面键/肩键/十字键/Home/Share）算"用户真的在用这台"。

界面侧零改动：`connectedNames` 已经把 active 排第一，大屏左上角键位图、
顶部手柄名、设置页顶部都读 `connectedControllers.first`，所以换手柄时
布局（任天堂/Xbox）和配色会跟着变。

实测（先 `--controller` 指定 Stadia，再随便按键）：
```
00:11:17 当前手柄 → Stadia（拉起参数）
00:11:24 当前手柄 → Pro Controller（按 Home）
00:11:29 当前手柄 → Stadia（按键）
00:11:38 当前手柄 → Pro Controller（按键）
```
后两条没有 Home 参与，证明普通按键已经能认设备。提交 `b6d52d8`。

**摇杆也算"在用这台手柄"**（老孙追问"摇杆没触发重新检测？"）。
第一版我把摇杆排除了，理由是怕漂移抢身份——不对，推杆就是明确的用户操作。
现在摇杆和按钮一样参与判定，门槛 `stickActivityZone = 0.34`（约 1/3 行程）。

中间我加过"持续 250ms"的时间过滤，被老孙否掉：**"别搞这么多限制，只要阈值即可"**。
确实——阈值本身已经能把漂移和推杆分开，再加时间窗是自己给自己找事。
最终就是一个阈值，单帧判断。提交 `e3b179e`。

**记一条判断标准**：这类输入过滤，老孙偏好"一个明确阈值"，不要叠时间窗、
持续时间、状态机这些额外条件。阈值不够就调阈值。

## MacDeck：R3 兼作确认 + 鼠标模式补全

**R3 = 确认**（老孙要的："避免不清楚当前键位造成歧义"）。放在
`DeckStore.action(for:)` 最前面一条 `if key == HIDKey.rightStickPress { return .confirm }`，
一条映射通吃大屏 / 设置页 / 各种确认层。

**L3/R3 怎么取**：`GCControllerDirectionPad` **没有** `button` 成员（编译直接挂），
要从 `controller.physicalInputProfile.buttons[GCInputLeftThumbstickButton /
GCInputRightThumbstickButton]` 拿。键码用 15/16。

**鼠标模式补全**（原来只有左摇杆移动 + A/B 点击）：

| 输入 | 功能 |
|---|---|
| 左摇杆 | 移动光标（L/R 调 0.5x~2.5x） |
| 右摇杆 | 滚动，垂直+水平，像素单位 |
| A / B | 左右键 |
| R3 | 中键 |
| L3 | 按住拖动，再按松开 |
| ZL / ZR | ⌘[ / ⌘] 后退前进 |
| 十字键 | 方向键 |
| - / + | PageUp / PageDown |

实现坑：
1. **滚动必须用 `.pixel` 单位 + 亚像素累积**。每帧 moveto 一点点会被系统吞，
   要攒够 1px 才发 `CGEvent(scrollWheelEvent2Source:units:.pixel,wheel1:wheel2:)`。
2. **拖动时不能只 `CGWarpMouseCursorPosition`**：被拖的窗口收不到
   `leftMouseDragged` 就不会动。要直接 post dragged 事件（它自己会移动光标）。
3. **`stop()` 里必须补一次 leftMouseUp**。退出鼠标模式时若还在拖动，
   不补的话整个系统会一直处于拖拽状态，用户鼠标就"粘"住了。
4. `mouseMode` 分支在 `heldKeys` 更新之前 return，所以鼠标模式下的按键
   不进组合键状态机；Home 例外（`key != 13` 才拦）。

提交 `6717739`。
